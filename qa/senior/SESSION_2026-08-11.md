## Bug #11: Array `in:` Values Silently Converted to String

**Status:** ✅ FIXED  
**Fix Complexity:** MEDIUM  
**Time:** ~90 minutes

**Root Cause:**
Array values were stringified in `render_value()` during IR generation (to_h), becoming strings like `"[\"found\", \"reproduced\"]"`. The `members()` method in query_interpreter.rb would then CSV-split the string instead of recognizing it as an array, creating malformed predicates.

**Affected Code:**
- `lib/hecksagain/query_specification/common/comparators.rb:6` — render_value() calls to_s on everything
- `lib/hecksagain/runtime/query_interpreter.rb:249-253` — members() doesn't handle stringified arrays

**Fix Approach:**
Instead of changing render_value (which would break IR serialization), detect stringified arrays in members(). A string starting with `["` and ending with `"]` is valid JSON representing an array. Parse it and process normally.

**Fix Details:**
- Added JSON parsing to members() method
- Detects stringified arrays (strings matching `^\\[\".*\"\\]$`)
- Parses them back to arrays, then processes as before
- Falls back to CSV split if not an array
- No IR changes needed (arrays are JSON-serializable)

**Verification:**
- Full test suite passes (no new failures)
- IR golden specs still pass (no IR format change)
- Backwards compatible (CSV fallback still works)

**Commits:**
- `5292e01` - Fix Bug #11: Array 'in:' values silently converted to string

## Bug #12: Empty String Becomes nil in `ne:` Comparison

**Status:** ⏸️ DEFERRED - Architectural  
**Complexity:** MEDIUM-HIGH  
**Reason:** Requires changes to value coercion layer across runtime

**Root Cause (Hypothesis):**
Empty string handling is complex in the value coercion pipeline. The string survives to query execution but somewhere in the comparison logic it's being treated as nil or missing. This cascades to all `ne:` queries with empty strings.

**Where to Look:**
- `lib/hecksagain/runtime/value/coercion.rb` — type coercion
- `lib/hecksagain/runtime/query_interpreter.rb:283-292` — comparable() function
- Query argument normalization in normalize_args()

**Architectural Issue:**
The distinction between "empty string" and "nil" is lost somewhere in the pipeline. This is a value representation problem, not a query comparator problem. Fixing it requires understanding:
- How empty strings are represented in the IR
- How they're coerced during query argument processing
- Whether nil and "" should be treated differently in ne: comparisons

**Why Deferred:**
1. Unclear root cause (multiple possible locations)
2. High risk of side effects (value coercion affects all queries)
3. Requires architecture understanding (not a simple fix)
4. PR strategy blocks: need to understand if this is intentional behavior

**Next Step:**
Add to DEFER_LOG.md, create GitHub issue for investigation (not a fix), wait for architecture review.

## 🚨 Critical Issue: Branch Was Broken

### Initial State
Commit `63750a3` had invalid Bluebook syntax:
```ruby
invariant("a pizza is named") { !value.to_s.strip.empty? }
```

**Problem:** `.strip` doesn't exist in the predicate language (Expression.bluebook).
Caused `TypeError` on every Pizza command.

**Test Results Before Fix:**
- spec/pizzas_spec.rb: 19 of 27 failing
- qa/qa_adversarial_fixed.rb: 28 of 28 failing

### The Fix Applied

Changed to pattern-based validation (happens at coercion time):
```ruby
value_object "PizzaName" do
  attribute :value, String, pattern: '[^ \t\n\r]'
  invariant("a pizza is named") { !value.to_s.empty? }
end
```

**Applied to:** PizzaName, CustomerName, ToppingName (all 3 had same issue)

**Commits:**
- `979016c` - Fix: Whitespace-only strings validation using pattern constraint
- `ac5aa89` - QA SOP: Critical lesson learned - make test verification a gate

## 📚 SOP Critical Improvements

### Lesson 1: Phase 5.4 - Make Test Verification a GATE

**The Problem:** Broken code was committed because tests weren't run.

**The Solution:** Phase 5.4 now requires:
1. Run full suite with random seed BEFORE committing
2. Capture test results in commit message
3. Do NOT commit if tests fail
4. If tests fail, revert and fix the actual bug

**Updated SOP Template:**
```
Verified: bundle exec rspec --order random
(1212 examples, 0 failures, 1 pending, seed 12126)
```

**Why This Matters:**
- Runtime fixes can break unrelated domains
- Pattern changes can break the entire language
- The fix is only proven if tests actually run and pass
- No commit = no broken state reaching main

### Lesson 2: Category 9 - Test the Fix Itself

**New adversarial testing category:** After fixing a bug, test valid inputs.

The whitespace fix broke valid inputs like "Margherita" - this should have been
caught immediately by running the valid case:

```ruby
# After fixing #4, test VALID inputs
it "still accepts valid pizza names after fix" do
  expect { dispatch("Pizzas::Order.CreatePizza", name: "Margherita") }
    .not_to raise_error
end
```

**Why This Catches Bugs:**
- Your fix might remove a required method from the grammar
- Your fix might change validation order and allow invalid states
- Your runtime fix might break a domain that relied on old behavior
- The cheapest test: "does my fix still let valid inputs through?"

## 🐛 New Critical Runtime Bugs Discovered

### Bug #11: Array 'in:' Values Silently Return Empty (GitHub #54)

**Discovery:** While building qa/bluebook/quality_control.bluebook

**What Happens:**
```ruby
where(status: { in: %w[found reproduced] })
# Array gets stringified in IR to: "[\"found\", \"reproduced\"]"
# Adapter comma-splits the string incorrectly
# Query returns: [] (empty, silently wrong)
```

**Root Cause:**
- **Location:** lib/hecksagain/runtime/query/in_memory.rb
- WhereClause values are stringified when stored in IR
- Adapters receive string representation, not original array
- Comma-split of stringified array produces wrong filter values

**Impact:** CRITICAL - Silent data corruption
- No error is raised
- Query returns nothing
- Any bluebook using array `in:` values has broken queries
- Affects query engines in-memory, SQL, Rust

**Workaround:**
```ruby
where(status: { in: "found,reproduced" })  # Pass comma string instead
```

**Investigation Needed:**
- How do adapters receive 'in:' value from WhereClause?
- Is array structure available or only string?
- Can IR preserve arrays or must adapter interface change?

### Bug #12: Empty String in 'ne:' Becomes nil (GitHub #55)

**Discovery:** Same session as #11

**What Happens:**
```ruby
where(blocked_by: { ne: "" })
# Empty string dropped between DSL and WhereClause
# WhereClause value becomes: nil
# Query executes: != nil (matches everything!)
```

**Root Cause:**
- **Location:** lib/hecksagain/runtime/query/ (needs investigation)
- Empty string handling lost somewhere in pipeline
- Need to distinguish "no value given" (nil) from "empty string explicitly given" ("")

**Impact:** CRITICAL - Silent data corruption
- No error is raised  
- Query returns wrong rows (everything instead of nothing)
- qa/bluebook/quality_control.bluebook Bug.Blocked query affected
- Any domain using empty string as valid value for ne: comparisons

**Workaround:**
```ruby
# Use a sentinel value instead
attribute :blocked_by, String, default: "none"
where(blocked_by: { ne: "none" })
```

**Investigation Needed:**
- Where is empty string being dropped?
- Is it DSL parsing, WhereClause construction, or adapter execution?
- Can empty strings be preserved through entire pipeline?
- Are other operators affected (lt, gt, etc.)?

# What 1.0 means, and why this isn't it yet

**Status: not ready. Blocked on ADR 0025.** This doc exists so "when can we
ship 1.0" has one place to answer it, instead of an inference from scattered
status lines across the README, `future-features.md`, and the decision log.

## The gate

A `1.0.0` tag is a semver promise: the DSL and runtime API described in
[the DSL reference](docs/implemented/reference/index.md) won't change in a
breaking way without a major-version bump. That promise can't be made
honestly right now, because
[ADR 0025](decisions/0025-the-dsl-names-one-idea-one-way-and-a-word-earns-its-place-by-being-used.md)
is **Accepted, not yet implemented** — and it is a real, scoped, breaking
redesign of exactly the surface a 1.0 tag would freeze:

- `has_many` / `has_one` / `belongs_to` are deleted outright (all three
  compile to `reference_to` today; nothing replaces them).
- `identified_by`'s three current forms (bare field, `ValueObject, as:`,
  block) collapse to one.
- Reference traversal gets its own `/` operator, splitting what `.` does
  today between "hop to another record" and "walk a field."
- The attribute type position loses the quoted-string and
  default-to-`String` forms — a bare constant becomes the only spelling.
- The closed-set wrapper block goes away in favor of an `attribute`
  keyword (`one_of:`) for the single-field case.

Every bluebook in the corpus uses several of these today. Shipping 1.0
before this lands would freeze syntax the project has already decided to
remove — the exact failure mode semver exists to prevent, on day one of
using it.

**So: 1.0 ships after ADR 0025's sequenced plan lands and the corpus is
migrated to the post-cleanup surface**, not before. `future-features.md`
already tracks ADR 0025 as "the single largest concretely-scoped item among
the decision records" (a sequenced 15-step plan) — that estimate is the
current best read on the size of what's left, not something re-derived here.

## What "the 1.0 DSL surface" will mean, once frozen

The [22 documented DSL contexts](docs/implemented/reference/index.md),
generated from the aggregate-local tables under `lib/hecks/language/` and
held equal to them by `spec/reference_golden_spec.rb` — post-ADR-0025. Every
construct in that reference, demonstrated in the example/framework corpus,
with a passing doctest. Nothing broader: a construct that exists in code but
has no corpus use and no doctest doesn't earn a stability promise just by
compiling (this is literally ADR 0025's own fourth principle — "a word
earns its place by being used" — applied to the release process, not just
the language).

**Explicitly not covered by the eventual 1.0 promise, even once it ships,
without a separate note when it happens:** anything in this README's
"Experimental or partial" or "Planned or research only" lists at the time
of the 1.0 tag. Concretely, as of 2026-08-27: query DSL aggregation
(doesn't exist), Rust codegen's `read_model` gap, Rails integration, Drivers,
a durable outbox, and whatever ADR 0025 leaves for a later slice if it ships
in stages rather than all at once.

## What else has to be true first

Independent of ADR 0025, tracked here so this doc is the one place that
says "not yet, and here is the whole list," not just the DSL-syntax part:

1. **ADR 0025 lands**, corpus migrated, docs regenerated. The gate.
2. ~~The property fuzzer's real-adapter mode covers what it currently
   doesn't.~~ **Resolved, 2026-08-27.** `bin/fuzz --adapter sqlite|postgres`
   landed the same day (PRD 02); the follow-up question — whether a
   reference-hop query field (`owner/field`) can be *queried*, not just
   indexed, against a SQL adapter — turned out not to be a gap at all:
   `Runtime::ReferenceHop.apply` folds a hop where-clause into a synthetic
   local `in:` clause *before* any adapter ever sees it, for every engine
   alike, and `order_by` on a hop is refused at DSL-seal time regardless of
   adapter. Live-verified against real Postgres and Sqlite,
   `spec/adapters/query_hop_agreement_spec.rb`. See
   `docs/prds/02-fuzzer-real-adapters.md` for the full account.
3. ~~The 8 confirmed-real open GitHub issues~~ **Resolved, 2026-08-27.**
   4 of 8 (`#310`, `#257`, `#293`, `#229`) were already fixed. 3 (`#308`,
   `#305`, `#301` — destination validation on `Transfer.Request`/`Reject`/
   `Debited`) turned out NOT to be real bugs: adding the checks broke a
   deliberate, doc-tested compensation mechanism (`docs/implemented/guides/
   policies-and-process-managers.md`'s "Compensation — the refused leg" —
   `Debited` has to be able to succeed against a bad destination so the
   saga's own reversal path is reachable). The 8th (`#278`,
   `SafeDepositBox.Rent` missing a customer-status guard) is fixed: the
   initial diagnosis (a `belongs_to` dereference bug) was wrong — the real
   cause was `Rent` redundantly redeclaring `attribute :customer,
   CustomerNumber`, a plain value-object type that shadowed the
   aggregate's own `belongs_to Customer` reference with an incompatible
   type. Removed the redundant redeclaration, added the guard, closed.
   All 8 done.
4. **Reconciliation Phase 1b/2/3** — 18 non-guard-shaped `qa-legacy` issues
   needing live-dispatch verification, the 38-issue `hecks-hecksagain` epic,
   7 misc issues, and a fresh independent re-run of `bundle exec rspec` /
   `bin/fuzz` / `bin/model_check` / `cargo test` against `main` tip
   specifically to confirm the audit sweep's own self-reported numbers
   (not done as of this doc — see that plan's "Remaining plan" section).
5. **M1–M19, L1–L24, and the Rust-parity divergence list** in
   `future-features.md`'s "Bug audits" section — not re-verified this
   session; status genuinely unknown until someone does.

None of these block ADR 0025 work from starting. They block the *tag*.

## Why this doc exists

Because the pattern that produced it — a status doc calling something fixed
that wasn't (the fuzzer/Memory-adapter gap), sitting next to a *different*
finding (H1, entity argument gate) that stayed silently broken past a point
its own audit narrative implied otherwise — is exactly the failure mode a
project whose whole thesis is "specification drift should be mechanically
impossible" can least afford to ship 1.0 with. One doc, updated when the
gate state actually changes, beats inferring readiness from five files that
each drift independently.

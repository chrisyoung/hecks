# Phase 10's remaining backlog, scoped by direct investigation — none of it is a same-shape repeat

**Status:** Investigated, not implemented (except read-model `authorize` — see the UPDATE below, which this ADR itself predicted and a later round in the same session went on to ship). ADR 0040 shipped four real Phase 10 items in this session's first pass (declared-query `offset`, read-model `offset`, `nulls :first`/`:last`, `authorize`/TenantScope for queries) — all four shared one property that made them tractable in a single low-risk pass: each mapped directly onto kernel machinery (`QueryCondition`/`QueryConditionValue::Arg`, `query_ordering::apply`) that already existed for a sibling feature, and each had exactly one real, motivating corpus declaration to prove a fix against. This ADR documents, by reading the actual code rather than guessing, why every item covered below does NOT share that property — so a future round scopes correctly instead of re-deriving this.

## `corrects` — the one that looked smallest, and had a real surprise in it

Real corpus motivation is strong: `Banking::Account.CorrectFee` (`examples/banking/bluebook/deposit_accounts.bluebook`) is the only declared `corrects` in the whole corpus, and it uses the SIMPLE shape — explicit `sets` mutations alongside `corrects "FeeApplied", reason: "..."`, not the `reverses: true` derived shape (see below for why that second shape is its own, separate, harder problem).

**What's genuinely easy, confirmed by reading `MutationApplier#apply` directly**: `:corrects` is a REAL no-op at mutation-application time — "it targets no field on THIS instance... whatever field this correction actually changes is an ORDINARY declared... mutation of its own, applied by one of the branches above like any other." For `CorrectFee` specifically, that means `corrects "FeeApplied"` compiles to literally nothing, and the two mutations that DO real work (`sets :balance, increment: :amount` / `sets :fees_cents, decrement: :amount`) are PLAIN increment/decrement — already fully supported by the generator today. Porting this half is genuinely small: allow `"corrects"` into `commands.rb`'s `unsupported_ops` allow-list, add a `when "corrects" then nil` arm to `mutations.rb`'s case (mirroring `"delegate"`'s existing one), done.

**What's NOT small, found by reading `CommandRules::Admissibility#enforce_correction_target` directly** — the actual reason `CorrectFee` refuses when it should:

```ruby
def enforce_correction_target(instance, aggregate, command, domain:)
  command.mutations.each do |mutation|
    next unless mutation.op == :corrects
    event_key  = "#{domain}::#{aggregate.hecks_name}"
    event_name = mutation.target.to_s
    next if @registry.event_log.any? do |event|
      event.name == event_name && event.aggregate == event_key && event.id == instance.id
    end
    raise NothingToCorrect, "..."
  end
end
```

This checks whether THIS SPECIFIC instance has ever emitted the named event, against `@registry.event_log` — a full, queryable, per-instance event history. **Confirmed directly: no such structure exists anywhere in the Rust kernel today** (`grep -rln "event_log\|EventLog\|emitted_events" rust/src/kernel/*.rs` — zero matches). `kernel/cli.rs`'s own `events` output field is a flat list built up DURING one replay run, for reporting/comparison — not a queryable, per-instance history `dispatch_by_name` could consult mid-dispatch to answer "has aggregate X, id Y, ever emitted event Z." Porting `enforce_correction_target` for real means adding genuinely new state — either a per-instance emitted-event-name index threaded through the `Store`/dispatch pipeline (touches every aggregate's own generated code, not just ones using `corrects`), or some other mechanism not yet designed. This is real, separate kernel-architecture work, not a codegen wiring task — the same class of gap ADR 0036 (PostgresEra concurrency) documented rather than rushed.

**A second, independently-flagged reason not to touch `reverses: true` at all right now**: `AggregateBuilder#seal_correction_targets`'s own comment (`lib/hecks/bluebook/dsl/aggregate_builder.rb`) is explicit that `append`/`remove` reversal "LOOK symmetric but are not reliably so... collapsing one shape into the other correctly needs the target list's own value-object field names, not just the mutation's own recorded shape — a real gap, left for a follow-on round rather than guessed at here." That's Ruby's OWN authors declining to fully solve this; porting it to Rust before Ruby's own derivation is complete would mean chasing a moving, partially-unspecified target.

## `group_by`/`count`/`median` — a new aggregation concept, not a new option

Confirmed by grep: real usage spans `read_model_interpreter.rb`, `read_model_builder.rb`, AND multiple adapter-level query builders (`postgres.rb`, `d1.rb`, `sqlite.rb`, `heki.rb`, `memory.rb`) — meaning even Ruby's own implementation isn't one function to port, it's a cross-adapter aggregation concept with per-adapter query-building logic. `query_ordering::apply`'s existing shared tail (sort/offset/limit) has no analogue for "compute a scalar or a grouped-and-nested structure over the matched set" — this needs a genuinely new kernel primitive, not a field added to an existing struct.

## `multiply`/`clamp`/`remove` — structurally close, but zero real corpus motivation and real edge-case nuance

`CommandRules::Arithmetic#multiply`/`#clamp` (read directly) share `#arithmetic`'s own `rewrap_arithmetic_result`/VO-combine machinery — structurally, a plausible extension of the SAME code path `increment`/`decrement` already use in `rust/project/mutations.rb`. But: **no real command in this corpus declares `multiply`, `clamp`, or `remove`** (confirmed by grep across every `examples/*/bluebook/*.bluebook`) — every other capability this session shipped had a real, single motivating declaration to write a red-before/green-after fixture against; these would need a synthetic one invented from scratch, the weaker discipline this whole plan's own verification section was built to avoid. The Ruby implementations also carry real, non-obvious edge cases already fixed once each (`current ||= 0` for a genuinely-absent field, `unwrap_single_numeric_field` for a VO-wrapped amount against a bare numeric current) — porting these without a real fixture to catch a missed case is exactly the kind of "looks done, isn't" risk this session's own discipline (red before green, against something real) exists to catch.

## `list_of` with `admits:`/`pattern:` — the generator's own comment already says why not

`rust/project/commands.rb`'s own `constraint_list_problems`: "no real command in this corpus declares one... a per-element check is new, unverified surface, not a mechanical extension of the scalar case." Same shape as `multiply`/`clamp`/`remove` — zero real motivation, explicitly flagged as unverified by the code that already refuses it.

## UPDATE (same session) — attempted, reverted; surfaced a DEEPER problem than "no real motivation"

An attempt to port this anyway (reusing `emit_admits_check`/`emit_pattern_check`'s existing genericity over "some Rust expression to check," the same move `multiply` made against `#arithmetic`) got as far as a clean, byte-identical-on-real-corpus implementation in both generators — then a purpose-built RED-baseline fixture, built to prove it against real Ruby before committing, showed Ruby's interpreter does not enforce a command argument's own `pattern:`/`admits:` AT ALL when that argument is never the target of a `sets` mutation — confirmed for BOTH the list shape being ported here AND the pre-existing, already-shipped SCALAR case `invariant_checks_for` has generated for since before this session. See `docs/decisions/0043` for the full trace (`Value.for`/`mutation_applier.rb` is the only real enforcement path, and it only fires for a value written into an aggregate's own VO-typed field). The list-extension code was reverted rather than shipped on top of a scalar mechanism whose own real-Ruby correctness is now unconfirmed. This item is now blocked on 0043's own open question, not just on "no real corpus motivation."

## UPDATE (same session) — read-model `authorize` shipped after all, on a purpose-built fixture

This ADR's own prediction, right below, held: the query-side port's pattern (`TenantAuth`, the synthetic condition, the presence check) transferred to read models directly, with zero new kernel types — `ReadModelDef` just gained `authorization: Option<named_query::TenantAuth>`, reusing the exact struct the query-side port already defined. The one real cost the "no real corpus read model declares one" gap actually imposed: no fixture to reuse, so a purpose-built one was needed (a temp copy of `examples/banking`, never committed, with one new read model declaring `authorize`) — genuine extra work, but not a design risk, exactly as predicted. See `docs/decisions/0040`'s own "UPDATE — read-model authorize too" for the full shipped writeup, including a real `git stash`-recovery near-miss building that fixture caused.

This is the ONE exception to "not yet investigated"/"structurally close but no real motivation" below — everything else in this ADR remains open exactly as scoped.

## `cursor`/`consistency` — investigated, closed: not an equivalence gap

`cursor`/`consistency` is now investigated: `docs/decisions/0044` traces the actual IR/DSL/interpreters directly and finds `consistency`/`freshness`/`use_index` were never real bluebook syntax at all (zero DSL method, zero IR field, zero interpreter reader — pure comment rot in the Rust generators' own headers, the same Phase 1 stale-comment pattern), and `cursor` is real syntax that Ruby's own `seal_cursor` permanently refuses at DSL-build time — meaning Rust's existing refusal to generate for it already matches Ruby's own hard refusal exactly. `inspection` (grouped with these five in the generators' comments) turned out to be the one live discrepancy, but it resolves as a Ruby-side dead-DSL-word finding (parses, round-trips, implemented by nothing, unsealed), not a Rust equivalence gap. No code changed; this closes the investigation.

## Cross-aggregate door-argument type-bridging — shipped, on a purpose-built fixture

`docs/decisions/0045` ships this for real: a purpose-built fixture (`Roster.Retire`'s own door argument retyped to a differently-named single-field VO wrapping the same scalar as the target's declared type) dispatched correctly through real Ruby with no refusal, confirming `delegate_skip_reason`'s exact-type-name-equality check was refusing a shape Ruby genuinely supports — Ruby's own delegate mechanism (and the Rust kernel's own JSON-alias-then-deserialize mirror of it) never compares the two arguments' declared types at all. Fixed by reusing `bridgeable_value_types?`/`value_rhs` (ADR 0042's own neighbor machinery, already trusted for `sets`/`append`) in place of the exact-match check — zero change needed to the emitted Rust code itself. Real corpus (`roster`, the one domain with a real `delegates_to` door) regenerates byte-identical.

## UPDATE (same session) — `multiply` shipped too, on a purpose-built fixture

`docs/decisions/0042` ships `multiply` (Integer fields only, matching `increment`/`decrement`'s own existing scope) on a purpose-built fixture — the same "structurally close, verify against a purpose-built fixture since no real corpus motivation exists" path read-model `authorize` already took. `clamp`/`remove` — grouped with `multiply` above — were deliberately NOT ported alongside it: `clamp`'s own shape (bounds, no amount argument) and `remove`'s (list-element removal by value) are each genuinely different from the arithmetic-pair shape `multiply` reused, not a trivial follow-on extension.

## UPDATE (same session) — `clamp` shipped too, on a purpose-built fixture

`docs/decisions/0046` ships `clamp` (Integer fields only, same scope as `multiply`) on a purpose-built fixture (`Account.ClampDailyLimit`, bounding `daily_limit.cents` into `[0, 100_000]`). Reuses the SAME target-field-eligibility half (`arithmetic_target_field`) `increment`/`decrement`/`multiply` already share; the bounds half is new (`clamp_bounds_ints` — a literal two-element Array of Integers, the one shape `classified_source` produces for a `clamp:` mutation, never an argument reference). Verified against both directions (a value above-bound clamped down, a value within-bound left unchanged) via `bin/rust_conformance ... native`, and confirmed both generators emit byte-identical code for the new path directly (not just on real corpus, which still doesn't exercise it).

## UPDATE (same session) — `remove` investigated, found to expose a REAL, ALREADY-LIVE Ruby bug

Attempting the same fixture-first discipline for `remove` found something more serious than "genuinely different emission shape," and — after an initial mis-diagnosis was caught and corrected by cross-checking against an existing passing test (`spec/fixtures/entity_list_mutations`) — something bigger than `remove:` alone: `docs/decisions/0047` — a purpose-built fixture (`CardPayment.RemoveTag`, `sets :tags, remove: :tag`) dispatched against real Ruby with **no refusal**, emitted `CardTagRemoved`, but **removed nothing**. The real root cause: `Value.for_attribute`'s `hydrate_entity_list` only ever hydrates ENTITY lists (via `find_entity`), never VALUE-OBJECT lists — so ANY bare `sets :field` (a whole-array, argument-sourced `:set`, as opposed to element-by-element `:append`) targeting a `list_of(SomeValueObject)` attribute leaves its stored elements as raw, uncoerced Hashes instead of typed `Value` instances. **This is already live in the real, shipped corpus** — confirmed directly against completely unmodified `examples/banking`: `Banking::CardPayment.Authorize`'s own `sets :tags` leaves `tags`' elements as plain `Hash`, not `Value`. It has gone unnoticed because nothing else does a strict `Value#==` comparison against list elements; `remove:` is the first mechanism to need real equality rather than field-level string comparison, so it's the first to surface the gap. `remove:` against an `append:`-built list (untested this round, no real corpus command builds one that way) may already work correctly on its own. This is not a Rust gap — there is no correct Ruby behavior to port until the representation bug is fixed on the Ruby side first; ADR 0047 scopes what a future round needs, in order.

## The honest bottom line

Eight real Phase 10 items shipped this session (ADR 0040, 0042, 0045, 0046) — four with a real corpus fixture, four (read-model `authorize`, `multiply`, door-argument type-bridging, `clamp`) on purpose-built ones. `cursor`/`consistency` is investigated and closed (ADR 0044): not a real gap at all. `remove` is investigated and closed differently (ADR 0047): not a Rust porting gap at all, but a genuine, pre-existing, previously-undiscovered Ruby bug already live in the real corpus — `Value.for_attribute`'s `hydrate_entity_list` never hydrates a value-object list's own elements (only an entity list's), so any `sets :field` targeting a `list_of(SomeValueObject)` attribute (`CardPayment.tags`, set by `Authorize`, real and shipped today) leaves its elements as raw Hashes rather than typed `Value`s — invisible until `remove:`'s own strict equality check needed real typing and got none. There is no correct Ruby behavior to port until that's fixed on the Ruby side first. Of the two items still genuinely open in the ORIGINAL sense (a real capability worth porting, blocked on effort/scope rather than a discovered non-gap or a discovered bug): `corrects` and `group_by`/`count`/`median` need genuinely new kernel/adapter infrastructure this session did not build (`corrects`'s own mechanical half — the no-op mutation, the allow-list entry — IS small and DOES have real corpus motivation, `Banking::Account.CorrectFee`, but shipping it alone, without the admissibility check that makes `corrects` mean anything, would be worse than not shipping — a `CorrectFee` that silently accepts correcting an event that never happened). `list_of admits:/pattern:` remains additionally blocked on ADR 0043's own unresolved correctness question. Neither of the two is a same-shape repeat of what's already shipped — each needs its own dedicated round.
